# 予定と期日からIssue・カレンダーを作る

予定・目標と最終期日から逆算し、完了条件のあるIssueと、それに対応するカレンダー予定を作成する。日本語で簡潔に進める。

## 入力と登録先

- 予定名、期待する成果、最終期日を読み取る。期日がなければ質問する。相対日付は実行時の現在日付と利用者のタイムゾーンで解決し、具体的な年月日を示す。解釈が複数ある日付は登録前に確認する。
- Issueの登録先（GitHubのowner/repo、またはLinearのteam/project）とカレンダーは、ユーザー指定と現在のプロジェクトで確立済みの運用を優先する。過去の別プロジェクトのIDや既定カレンダーを流用しない。接続先を読み取り、名前・ID・書き込み可否を確認する。
- GitHubとLinearの両方を使う運用なら、管理元と相互リンク方法を確認し、両方への登録が依頼・既存運用に含まれる場合だけ連携する。
- 登録先や不可欠な条件が不明なら、不足項目をまとめて短く質問する。その間も分解案と日程案は作る。登録先未確定の外部書き込みは行わない。
- このスキルを呼び出して「Issue化してカレンダーに追加」と頼まれた場合は、その範囲の作成を実施する。指定先と条件が確定済みなら重ねて承認を求めない。「案だけ」「下書き」「相談」の場合は登録しない。スキルの作成・編集依頼だけでは、実際の予定やIssueを登録しない。

## 分解と日程

1. 成果物から必要な工程を洗い出し、依存関係の順に並べる。各Issueは一つの確認可能な成果を持ち、原則として半日〜2日程度で進められる粒度にする。単純な予定を無理に細分化しない。
2. 各作業に、短いタイトル、目的、作業内容、完了条件、見積もり、依存する作業、開始日・期日を用意する。見積もりは推定と明記し、担当者・優先度・ラベルは指定または既存運用に従う。
3. 最終期日から逆算して、制作・実装だけでなく必要な確認・提出の時間も確保する。稼働日や一日の作業可能時間が未指定なら、まず日付単位の仮日程を作り、稼働条件の仮定を示す。締切を過ぎている、依存順が成立しない、必要工数が残り時間に収まらない場合は、範囲削減や期日変更の選択肢を提示し、実行不能な日程を確定登録しない。
4. 時刻指定がなければ、各作業の期日に終日予定を1件置く。作業期間をカレンダーに表示する依頼なら開始日〜終了日の終日予定にする。作業時間の確保を依頼された場合は、既存予定・空き時間・稼働時間を確認して時間枠を割り当てる。タイムゾーンは利用者の設定を優先し、不明なら確認する。
5. 外部登録の前に、作業名・開始日・期日・依存関係を簡潔な一覧で示す。これは進捗共有であり、条件が確定していればそのまま作成を続ける。

## 登録・再開・重複防止

- 利用可能なコネクター・API・CLIを優先し、実行環境のツール定義に従う。ツール名や未対応フィールドを推測しない。実際の仕様確認が必要なら、その環境の技術調査ルールに従う。
- 登録前に対象プロジェクトのIssueと対象期間のカレンダーを検索する。同じ目標・成果・日付に対応する既存項目を確認し、重複作成しない。既存項目の変更は今回の依頼範囲に含まれるときだけ行う。
- Issueを先に作成し、返された実際のID・URLを取得する。説明に最終目標、作業内容、完了条件、見積もり、開始日・期日、依存関係を含める。期日や依存関係をネイティブなフィールドで扱えない場合は本文に記載し、その違いを報告する。親Issueは複数作業を束ねる必要がある場合に作る。
- カレンダーのタイトルは `[Issue識別子] 作業名`、説明にはIssueのURL、完了条件、最終目標・期日を記載する。招待者・共有範囲・通知は依頼された場合だけ追加・変更する。
- 日付のみの予定は終日として扱う。終了日が排他的な形式では、1日の予定は翌日、期間の予定は最終日の翌日を終了日に指定する。対応しないツールで無理に深夜の時刻付き予定へ変換しない。
- 終日予定を作れない場合は、対応する別の接続手段またはICSを使う。ICSは日付・リンクを検証し、同じ目標・作業では安定したUIDを使う。ただしインポートが重複防止を保証するとは考えず、再登録前に既存予定を確認する。ファイルを生成しただけなら「インポート待ち」と報告する。
- 目標と各作業について、Issue ID/URL、カレンダーID、イベントID/URL、日付、実行結果の対応表を保持する。部分成功後はこの表と外部の現状を照合して未完了部分だけ再開する。再開用ファイルが必要なら対象プロジェクトの作業用領域に保存し、秘密情報は含めない。
- 書き込み結果が不明・タイムアウトの場合は、再作成前に検索して成功済みか調べる。認証・権限・接続エラーで同じ書き込みを繰り返さない。成功済みのIssueはカレンダー側の失敗だけで削除しない。

## 完了確認と報告

登録後は読み取りでIssueと予定を確認し、想定件数、タイトル、日付、登録先、Issueリンクを突き合わせる。作成済み・読み取り確認済み・未完了を区別し、Issueとカレンダーのリンクを短い対応表で返す。確認できなかった状態を完了と扱わない。

## 入力例

`10月30日までにポートフォリオを公開したい。GitHubのowner/repoでIssueに分解して、仕事用カレンダーへ追加して。`

登録先と年が会話から確定していれば、構成・素材準備・制作・動作確認・公開など必要な作業を逆算して登録する。不足している情報だけ確認し、既に指定されたことは聞き直さない。
